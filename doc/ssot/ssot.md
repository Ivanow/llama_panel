# SSOT — LlamaPanel (LLM Server Manager)

**Версия:** 2.0 (Deep Architecture)
**Дата:** 21.10.2026

> Единственный источник правды. Описывает не только структуру, но и бизнес-логику, алгоритмы и обоснование принятых архитектурных решений.

## 1. Философия проекта
**LlamaPanel** создавался как замена тяжеловесным оркестраторам (Kubernetes, Docker Compose) для локального ПК/сервера. Цель: дать возможность запускать разные GGUF-модели на одной GPU (GTX 1070 Ti) без ручного ввода команд в терминале, с защитой от падения системы из-за нехватки VRAM.

## 2. Журнал Архитектурных Решений (ADR)

### ADR 1: Почему Flask, а не FastAPI?
*   **Решение:** Flask.
*   **Обоснование:** Нам не нужна асинхронность на уровне веб-сервера. Запросы к API редкие (нажатия кнопок, опрос статуса раз в 10 секунд). Вся тяжелая работа (ожидание старта модели) делегируется в bash-скрипт `manager.sh` через `subprocess`. Flask проще устанавливается системно (`apt install python3-flask`) без создания виртуальных окружений (venv), что экономит место на SSD.

### ADR 2: Почему Vanilla JS, а не React/Vue?
*   **Решение:** Чистый JavaScript (ES6) и CSS Grid.
*   **Обоснование:** Отсутствие этапа сборки (Webpack, Vite, npm). Код фронтенда отдается Flask'ом напрямую в браузер. Легко отлаживается прямо в консоли браузера без source maps. Идеально для локального инструмента.

### ADR 3: Почему `tmux`, а не `systemd`?
*   **Решение:** Запуск моделей в фоновых сессиях `tmux` (например, `tmux new-session -d -s llama-asya`).
*   **Обоснование:** `systemd` требует прав `sudo`, создания `.service` файлов и `daemon-reload` при каждом изменении аргументов. `tmux` позволяет запустить процесс от имени обычного пользователя, легко к нему подключиться (`tmux attach`) для просмотра логов в реальном времени и убить одной командой.

### ADR 4: Почему JSON-кэш моделей на SSD, а не SQLite/PostgreSQL?
*   **Решение:** Файл `models_cache.json`, который обновляется по кнопке.
*   **Обоснование:** Сканирование HDD с 700+ ГБ моделей занимает секунды. Если делать это при каждом запросе страницы — интерфейс будет тормозить. JSON-файл на SSD читается за миллисекунды. База данных избыточна для хранения плоского списка путей.

### ADR 5: Как рассчитывается потребление VRAM (Эвристика)?
*   **Решение:** В `app.py` используется формула: `(Размер_файла_в_МБ) * (Количество_слоев / 99.0) + 500 МБ (на KV-кэш)`.
*   **Обоснование:** У `llama.cpp` нет API, которое заранее точно скажет, сколько памяти оно займет. Флаг `--n-gpu-layers 99` означает "загрузить всё". Эвристика предполагает линейную зависимость: если загружаем половину слоев (49), берем половину размера файла. Запас в 500 МБ страхует от падения при большом контексте (`--ctx-size`).

## 3. Поток данных (Data Flow)
1. Пользователь жмет "Старт" на карточке `asya-chat`.
2. JS отправляет `POST /api/action/asya-chat/start`.
3. Flask вызывает `subprocess.run(["./manager.sh", "asya-chat", "start"])`.
4. `manager.sh` читает `instances/asya-chat.conf`, проверяет занятость порта, запускает `tmux new-session ... llama-server ...`.
5. `manager.sh` в цикле стучится на `http://127.0.0.1:8080/health`.
6. Когда порт открывается, `manager.sh` возвращает код 0.
7. Flask возвращает JSON `{"output": "✅ ГОТОВО!"}` фронтенду.
8. JS перекрашивает огонек в зеленый.

## 4. Известные ограничения
*   Нет авторизации (предполагается использование в доверенной локальной сети).
*   Проверка VRAM приблизительная. Если модель упадет с OOM, интерфейс покажет "ERROR", но не сможет предотвратить это на 100%.
